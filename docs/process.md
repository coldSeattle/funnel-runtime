# Процесс работы с AI-агентами

Журнал того, как задача была декомпозирована, что делали агенты параллельно, что
проверялось и что отклонялось. Дополняется по ходу работы.

## Инструменты и настройка
- **Claude Code** — основной агент-оркестратор: разбор задания, дизайн, план, общий движок,
  интеграция, ревью, деплой. Субагенты — Claude Opus (реализация, ревью, скептики) и Claude Sonnet
  (чтение кода для заметок).
- **`CLAUDE.md`** — память проекта: стек, команды, инварианты (события без сырых ответов,
  аналитика только по уникальным сессиям, версии не удаляются), границы владения папками.
  Любой агент стартует с этого файла и не перечитывает всё задание заново.
- **`docs/design.md`** — контракт (API, схема БД, движок, события, правила агрегации).
  Агенты работают строго против него; отклонения — только через отчёт.
- **`.claude/agents/`** — роли: `backend-dev`, `frontend-dev`, `reviewer` (только чтение).
- **git worktree** — у каждого параллельного агента своя рабочая копия и своя ветка
  (`feat/backend`, `feat/frontend`), поэтому они физически не мешают друг другу.
  Ветки вливает в `main` только оркестратор после ревью.
- **Брифы задач** — на каждую задачу отдельный файл с точными значениями и решениями,
  отчёт агент пишет в файл; в контекст оркестратора попадает только статус.
- **Workflow-скрипты Claude Code** — детерминированная оркестрация ревью: несколько ревьюеров
  параллельно смотрят на код через разные «линзы» (контракт API; инварианты состояния и приёма
  событий; корректность аналитики и качество тестов), каждую серьёзную находку независимо пытается
  опровергнуть агент-скептик (для критичных — двое, с разных углов: воспроизвести / сверить с
  требованиями), подтверждённые находки одним списком уходят фиксеру, после фикса — узкое повторное
  ревью только его диффа. Не больше двух раундов исправлений на задачу.

## Декомпозиция
1. **Последовательно (оркестратор):** скелет, типы, zod-схема, движок с тестами. Это общий
   фундамент: если бы его писали параллельно, клиент и сервер разошлись бы в логике ветвлений.
2. **Параллельно:** backend (версии, сессии, A/B, ingest, аналитика + тесты) ∥ frontend
   (воронка, трекер, админка, дашборд). Пересечений по файлам нет: `server/` против `web/`.
3. **Параллельно:** генератор трафика ∥ деплой и README.
4. **Последовательно:** интеграция, e2e-прогон, итерация 2 на проде, теги.

## Решения, принятые при декомпозиции
| Проблема | Решение | Цена ошибки |
|---|---|---|
| Имя query-параметра для override (`variant`) лежит в конфиге, а клиент не знает конфиг до создания сессии | Клиент отправляет все query-параметры страницы, сервер сам берёт override и UTM | Лишнее поле в запросе |
| Трекер нужно покрыть тестами, а тесты компилируются без DOM | Ядро трекера без DOM (`web/tracker/core.ts`), браузерная обвязка отдельно | Нет |
| Два агента и один `server/app.ts` | Файл целиком передан backend-агенту | Нет |
| В спеке `computeResult(config, resolved, answers)`, в коде без `config` | Код прав (resolved уже содержит config), спека исправлена | Нет |

## Решения по отчётам агентов
| Вопрос агента | Решение | Почему |
|---|---|---|
| Ответы publish / rollback не описаны в контракте | Типы `ActivationResponse`, `UploadVersionResponse` в `shared/api.ts` | Фронтенд должен быть типизирован против того же контракта |
| Коды ошибок, которых нет в дизайне (`no_active_version`, `invalid_body`, `invalid_filter`) | Приняты и внесены в `docs/design.md` §5 | Одна таблица кодов для клиента и сервера |
| Когда засевать данные | Пустая БД всегда получает опубликованную v1; синтетический трафик — только с `SEED_ON_BOOT=1` | Прод никогда не стоит без воронки, а трафик — осознанный флаг |
| POST с `content-type: application/json` и пустым телом | Разрешён | Так шлют типичные fetch-обёртки на publish / rollback |
| События для истёкшей сессии | Принимаются | Очередь трекера и `sendBeacon` досылают события позже; TTL ограничивает воронку, а не аналитику |

## Ревью и отклонения

### Бэкенд (workflow: 3 линзы → скептики → фикс → повторное ревью, 6 агентов)
- **Контракт API:** найдено, что `POST /api/sessions` не валидирует тело: массив вместо строки в
  `variantOverride` или объект в `utm.source` давали 500 с текстом ошибки драйвера SQLite, а числовой
  `utm_campaign` сохранялся как `"42.0"`. Скептик воспроизвёл все четыре пробы → подтверждено.
  Исправление: Zod-схема тела с `satisfies z.ZodType<CreateSessionRequest>` (схема не может разойтись с
  контрактом — иначе не соберётся), плюс обработчик ошибок больше не отдаёт наружу текст внутренних 5xx.
  11 новых тестов, повторное ревью — «исправлено, новых проблем нет».
- **Инварианты состояния и приёма событий:** одобрено. Ревьюер отдельной пробой проверил, что сессия
  v3 после отката продолжает получать конфиг v3, а новая стартует на v1.
- **Аналитика и тесты:** одобрено; инвариант `Σ отвалов + до первого шага + дошли до результата = начали`
  держится и под фильтрами.
- **Мелкие замечания (9):** не блокировали, но все исправлены отдельным проходом — граничные коды ошибок,
  строгий ISO-8601 для `client_timestamp`, защита инварианта для «сирот» без `session_started`,
  недостающие тесты (закрепление версии после отката, скрытие шага вариантом B в v3). Повторное ревью:
  9 из 9 исправлено, новых проблем нет; 171 тест.

### Генератор трафика (workflow: реализация → 3 линзы → скептики → фикс → повторное ревью, 7 агентов)
- **Спецификация и рантайм:** одобрено. Засев при старте — только с `SEED_ON_BOOT=1`, после `listen`,
  без повторного засева; 120 сессий ≈ 0,3 с, `/api/health` отвечает во время засева.
- **Учёт:** одобрено. Ревьюер независимо прогнал 300 сессий на v1 и 300 на v3 и сверил каждое
  сохранённое событие с §7 (порядок, `next_step_id`, возвраты, скрытые шаги, `recommendation_expanded`).
- **Тесты:** подтверждена важная находка — тест «одинаковый seed → одинаковые числа» проходил только
  потому, что в нём подменён `Math.random`, которым сервер назначает вариант. Исправление: отдельный поток
  PRNG на каждую сессию, тест переименован и теперь проверяет, что `Math.random` вызывает только сервер.
  Решение оркестратора: назначение варианта остаётся случайным на сервере — клиент не должен его
  предсказывать; сверка генератора всё равно точная, потому что сравнивает с тем, что реально отправлено.

### Фронтенд (workflow поверх настоящего бэкенда: 3 линзы → скептики → фикс → повторное ревью, 8 агентов)
Ревью шло уже после интеграции: ревьюеры поднимали прод-сборку и проверяли контракт и события вживую в Chrome.
- **Интеграция и события:** каждый запрос клиента совпал с сервером; в БД ровно те события, что в §7.
  Подтверждено: неотправленные события прошлой сессии (после рестарта, 410 или `?variant=`) не досылались
  никогда. Исправлено: новый трекер досылает чужие очереди — у каждого события свой `session_id`, так что
  атрибуция не ломается.
- **UX воронки:** подтверждено — фокус клавиатуры падал на `<body>` при смене шага. Исправлено: фокус на
  заголовке нового вопроса. Находку «системная кнопка назад уводит из воронки» скептик опроверг (ТЗ этого не
  требует), но оркестратор всё равно взял её в работу: платный трафик из соцсетей — это в основном Android.
- **Требование оркестратора:** шрифты с Google Fonts — сторонний сервис, который ТЗ запрещает; перенесены в бандл.
- **Админка и дашборд:** одобрено, включая правило подписи отката и работу с токеном.

### Вторая итерация (workflow: реализация → 3 линзы → скептики → фикс, затем доводка)
- **Спецификация скрипта:** одобрено — все 14 проверок перечитывают данные с сервера, а не сверяют то, что
  скрипт сам сгенерировал.
- **Тесты:** одобрено. Ревьюер проверил их «мутациями»: подсунул сессии v1 конфиг v3, сделал whitelist
  событий слепым к версии, потерял аналитику v3 после отката — каждый раз падала именно нужная проверка.
- **Сервер и генератор:** подтверждено — вердикт «параллельный трафик» мог замаскировать реальную потерю
  событий. Исправлено: этот вердикт только если чужие сессии объясняют расхождение целиком.
- **Доводка по решению оркестратора** (скрипт будут запускать на проде): проверка 10 привязана к сессиям
  именно этого прогона; при любом сбое после публикации v3 скрипт сам возвращает v1 и предупреждает;
  «старая активная сессия» проверяется на незаконченной сессии v3; заголовок тихого логирования принимается
  только с loopback. Так как диск free-хостинга эфемерный, демо-сервер при старте сам проигрывает сценарий
  второй итерации — проверяющие всегда видят сравнение версий и историю отката.

### Финальное ревью всего репозитория (часть 1: сервер, скрипты, документация)
Три линзы на весь репозиторий и живой прод, каждую серьёзную находку перепроверял скептик.
- **Проверяющий по ТЗ:** все пять обязательных тестов из п. 7.1 действительно проверяют своё; на проде
  инвариант дашборда держится при любых фильтрах; повтор пачки даёт только `duplicate`.
- **Найдено и исправлено одной волной:** откат был «переключателем» — на свежем демо Rollback включал v3
  (теперь стек отмен, цель отката отдаёт сервер); overrides варианта обходили проверку конфига на открытой
  админке (теперь проверяется каждый вариант после слияния); в `answer_kind` можно было протащить сырой
  ответ, а в `step_id` — мусор (теперь только скаляры и шаги варианта); при «всех версиях» A/B смешивал два
  разных эксперимента (теперь сравнение внутри каждой версии).
- **Документация:** шаг «загрузите v3» в README не работал на демо, где v3 уже загружена; про сброс демо после
  сна не было предупреждения; «14 проверок» верно только с `--traffic`. Исправлено.
- **Осознанно не сделано:** запуск контейнера не от root — проверить Docker-сборку локально в тот момент было
  нельзя, а риск сломать деплой ради мелочи не оправдан; записано в ограничения.

### Финальное ревью фронтенда в роли проверяющего (3 линзы на прод-сборке, скептики, фиксы)
- **Админка и дашборд:** одобрено. Проверяющий пересчитал цифры A/B по каждой версии прямо из живого API
  (`stats.ts` против таблицы и против SQL), проверил откат по стеку (на свежем демо Rollback выключен,
  после публикации v3 — «Roll back v3 → v1?»), закрепление версии в двух вкладках, ошибки загрузки конфига.
- **Регрессии и тесты:** одобрено; новые ошибки приёма событий (`unknown_step`, `invalid_properties`)
  возвращаются по событию с HTTP 200, поэтому трекер не зацикливается на повторах.
- **Воронка:** подтверждено — в обязательное числовое поле можно было ввести одни пробелы (сохранялось как 0),
  а `0x10` и `1e1` принимались как числа. Интерфейс исправлен сразу; корень был в общем движке, который
  перепроверяет ответы и на сервере, — его исправили отдельным раундом с правом на `shared/`, с тестами на
  движок и на API.

### Живой прогон оркестратора (прод-сборка, настоящий API, Chrome)
Полный проход воронки со сверкой цепочки событий в БД. Поймано то, что ревью кода не видит: клик во время
анимации смены шага попадал в «Back» из-за сдвига вёрстки; главная кнопка частично уходила за нижний край
экрана; мультиселект позволял выбрать 4 из 3; заголовок «30 days» из варианта B протекал в вариант A. Всё это —
отдельный пакет UX-правок вместе со значимостью A/B на дашборде.
